# Demo Guide — คู่มือนำเสนอ

> **Prototype Disclaimer:** ระบบสาธิตต้นแบบเพื่อแสดงแนวคิดเท่านั้น ผลตรวจสอบ ใบรับรอง Badge สถานะ และสถิติทั้งหมดเป็นข้อมูลจำลอง ไม่มีผลทางกฎหมาย และไม่ใช่การรับรองจากสภา SME หรือ สคบ.

## ก่อนเริ่ม

1. `npm install` แล้ว `npm run dev` เปิด http://localhost:5173
2. เปิดหน้า **Demo** ที่ `/demo` (หรือกดปุ่มหลักบนหน้าแรก) — โครงสร้างเรียบง่าย ไม่มีเลข Scenario หรือ Full Journey ที่ผู้ใช้เห็น:
   - **ทดลองใช้งาน SME Trust ตั้งแต่ต้นจนจบ** — Primary Action เดียว (หน้าแรกและหน้า Demo) เริ่ม Demo หลักทันที ไม่ต้องเลือกเรื่อง: เชื่อมข้อมูลร้านค้า → ลงทะเบียน → ตรวจสอบอัตโนมัติ → ประเมินความน่าเชื่อถือ → แสดงผล Badge → ผู้บริโภคตรวจสอบ (11 ขั้นในตัวควบคุม) · ใช้ร้านค้าเดียวกันทุกขั้น · ร้านปกติไม่ต้องรอเจ้าหน้าที่ · ไม่ออกใบรับรองให้อัตโนมัติ · ถ้าข้อมูลไม่พอระบบแสดงสถานะจริงแทน Badge
   - **กรณีพิเศษ (เฉพาะกรณีจำเป็น)** — 3 เรื่อง แต่ละการ์ดมีปุ่ม "ทดลองกรณีนี้":
     - **กรณีร้านค้าไม่มี Marketplace และข้อมูลยังไม่พอ** — ลงทะเบียนด้วยตนเอง ผ่านการลงทะเบียน แต่ข้อมูลการขายยังไม่พอแสดง Badge (ระบบแนะนำให้ร้านเพิ่มเอง ไม่ส่งเจ้าหน้าที่) · ปุ่ม "ดูร้านที่ข้อมูลยังไม่เพียงพอ" เปิดหน้าร้าน M-002 จากข้อมูลตั้งต้น (ผลประเมิน — **ไม่ใช่ผลการตรวจคำขอลงทะเบียน** หน้าจอระบุไว้)
     - **กรณีข้อมูลร้านค้าไม่ตรงกัน — เจ้าหน้าที่ตรวจสอบ** — เจ้าของบัญชีร้านไม่ตรงผู้ยืนยันตัวตน → คิวงานเจ้าหน้าที่ → ตัดสิน → ระบบทำงานต่อ · ปุ่ม "เปิดคิวงานเจ้าหน้าที่" (`/o/exceptions`)
     - **กรณีร้านค้าถูกระงับการรับรองและการอุทธรณ์** — เจ้าหน้าที่ระงับจากหลักฐาน ร้านชี้แจงและอุทธรณ์ได้
   - **ดูเพิ่มเติม** (พับไว้):
     - **ดูผลลัพธ์โดยตรง** — เปิดจากข้อมูลจำลองที่มีอยู่โดยไม่เริ่ม Demo ใหม่และไม่สร้างผลประเมิน/Badge ใหม่: ผลประเมินความน่าเชื่อถือ (`/m/trust` ร้านตัวอย่าง M-001) · Assessment Badge (`/shop/M-001`) · ผู้บริโภคตรวจสอบร้านค้า (`/check`) · ถ้าข้อมูลเปลี่ยนจนไม่มีร้านในสถานะนั้น ปุ่มถูกปิดพร้อมคำอธิบาย · ถ้ามีการสาธิตค้างอยู่ จะถูกหยุดชั่วคราว แล้วกด "สาธิตต่อ" กลับขั้นเดิมได้
     - **ฟังก์ชันอื่นของระบบ** (6 เรื่อง) — ผู้ประกอบการสมัครสมาชิกและยืนยันตัวตน · สมัครร้านค้าและได้รับการรับรองหลังการตรวจสอบ · ผู้บริโภคร้องเรียนและร้านค้าช่วยแก้ไขก่อนส่งต่อ · คำเตือนและการอบรม · AI ตรวจสอบโฆษณา · AI ช่วยแก้ไขข้อร้องเรียน · ปุ่ม "รีเซ็ตข้อมูลสาธิตทั้งหมด"
   - ด้านล่างหน้าแยก **MVP / Prototype / Future Integration** และมี Prototype Disclaimer · ลิงก์เดิม `/demo/overview`, `/demo/v2/summary` และ `/m/marketplace-app` Redirect ไปหน้าปัจจุบัน
3. ใช้ **ตัวควบคุมการสาธิต** (เดสก์ท็อป: แผงด้านขวา ซึ่งเนื้อหาแอปเว้นที่ให้ จึงไม่บังปุ่ม · มือถือ/แท็บเล็ต: แถบล่างแบบย่อ แตะเพื่อเปิดรายละเอียด):
   - ชื่อการสาธิต, Progress (ขั้น x/y), บทบาทปัจจุบัน, คำแนะนำ, **ประเด็นนำเสนอ** และรหัสร้าน/คำขอที่ทุกขั้นใช้ร่วมกัน
   - **ถัดไป** ถูกปิดจนกว่าจะทำ Action สำคัญของขั้นนั้นเสร็จจริง พร้อมข้อความว่าต้องทำอะไร — ระบบไม่ทำ Action แทนผู้ใช้ และไม่เปลี่ยนหน้าด้วย Timer
   - ถ้าขั้นไปต่อตามเส้นทางปกติไม่ได้ (เช่น ชื่อร้านไม่ตรงกับร้านบน Marketplace) จะแสดงเหตุผลพร้อมปุ่ม **"เริ่มใหม่ (กลับไปแก้ไข)"** และ/หรือ **"เปิดกรณีพิเศษ"** — ไม่บังคับผลให้ผ่าน
   - ย้อนกลับไปขั้นที่ทำเสร็จแล้วจะแสดง **"ขั้นนี้ทำเสร็จแล้ว — กด ถัดไป ได้เลย"** ไม่ต้องกรอกหรือส่งซ้ำ · หน้าลงทะเบียนที่ส่งคำขอแล้วในการสาธิตนี้แสดง **"ส่งคำขอลงทะเบียนแล้วในการสาธิตนี้"** แทนแบบฟอร์ม (กันสร้างร้านซ้ำเมื่อย้อนกลับ / Refresh / เปิดหน้าลงทะเบียนอีกครั้ง)
   - เมื่อขั้นถัดไปเป็นอีกบทบาท จะมี **Role Transition** อธิบายเหตุผลและขอยืนยันก่อน แล้วเปิดรายการเดียวกัน (ID เดิม) ให้
   - ถ้าขั้นถัดไปอยู่หน้าเดิม จะไม่โหลดหน้าใหม่ — ข้อมูลที่กรอกในฟอร์มไม่หาย
   - ระหว่างเปิดหน้าของขั้นถัดไป ปุ่ม **ถัดไป / ย้อนกลับ** ถูกปิดชั่วครู่จนหน้าแสดงเสร็จ (กันกดซ้ำ)
   - ถ้าเครือข่ายสะดุดจนโหลดหน้าไม่สำเร็จ จะแสดง **"โหลดหน้านี้ไม่สำเร็จ"** ให้กด "โหลดหน้าใหม่" — ข้อมูลและขั้นตอนอยู่ครบ
   - **ย้อนกลับ** · **เริ่มเรื่องนี้ใหม่** (คืนข้อมูลเป็นจุดเริ่มต้นของเรื่อง ไม่สร้างข้อมูลซ้ำ) · **หน้า Demo** · **ออกจากการสาธิต** (หยุดชั่วคราว กลับมาต่อได้ด้วย "สาธิตต่อ" บนหน้า Demo)
   - Reload หน้าได้ ตัวควบคุมจะอยู่ที่ขั้นเดิมพร้อม Context เดิม
4. จบแต่ละเรื่องจะเปิด **หน้าสรุป** (ผลลัพธ์จริง ขั้นที่ทำ สิ่งที่เกิดขึ้นในระบบ ประโยชน์) พร้อมปุ่ม **"จบการสาธิต"** และ **"เริ่ม Demo ใหม่"**
5. บัญชีผู้ประกอบการตัวอย่างทุกบัญชีใช้ PIN **123456** (เบอร์ 0810000001–0810000012)

### จำลองหน้าจอ โทรศัพท์ / iPad / โน้ตบุ๊ก

เลือกได้ 2 ทาง: ปุ่ม **จำลองหน้าจอ** บน Topbar (จอแท็บเล็ตขึ้นไป) หรือ **Demo Mode → มุมมองหน้าจอ (Responsive)** (ทุกหน้า รวมหน้า Welcome/ลงทะเบียน)

| อุปกรณ์ | ขนาด (CSS px) | รูปแบบเมนู |
|---|---|---|
| โทรศัพท์ | 390 × 844 (หมุนเป็น 844 × 390 ได้) | Bottom Navigation |
| iPad | 820 × 1180 (แนวนอน 1180 × 820) | แนวตั้ง: Bottom Navigation · แนวนอน: Sidebar |
| โน้ตบุ๊ก | 1366 × 768 | Sidebar + Topbar |

- แอปแสดงใน iframe ขนาดเท่าอุปกรณ์จริง Breakpoint จึงทำงานเหมือนบนอุปกรณ์นั้น (ย่อให้พอดีจออัตโนมัติ แสดง % ที่ย่อบนแถบเครื่องมือ)
- สลับอุปกรณ์ได้ตลอด โดยไม่โหลดหน้าใหม่ — หน้าและข้อมูลที่กำลังสาธิตยังอยู่ (เปลี่ยนอุปกรณ์จะเริ่มที่แนวตั้งเสมอ)
- ภายในกรอบจำลอง ใช้แอปได้ปกติทุกบทบาท; ข้อมูลใช้ localStorage ชุดเดียวกับหน้าต่างหลัก
- ปุ่ม **ออกจากโหมดจำลอง** กลับไปแสดงเต็มจอที่หน้าเดิม · URL ของหน้าจำลอง (`/preview?device=…&path=…`) แชร์/Reload ได้

## ผู้ประกอบการสมัครสมาชิกและยืนยันตัวตน

**วัตถุประสงค์:** เริ่มใช้งานได้ง่ายด้วยมือถือ: OTP, e-KYC จำลอง และ PIN จนได้สถานะ "ยืนยันตัวตนแล้ว (Level 1)"

**กลุ่มผู้ใช้:** ผู้ประกอบการ · **เวลาโดยประมาณ:** ≈ 4 นาที · **Key Message:** ผู้ประกอบการเริ่มต้นได้ภายในไม่กี่นาที และทุกร้านผูกกับตัวตนที่ยืนยันแล้ว

| # | มุมมอง | หน้าจอ | สิ่งที่ต้องทำ | เงื่อนไขก่อนกด "ถัดไป" |
|---|---|---|---|---|
| 1 | ผู้ประกอบการ | `/` | **หน้าเริ่มต้น** — แนะนำระบบ แล้วกด "ถัดไป" (หรือปุ่ม "เริ่มลงทะเบียน")<br>💡 ผู้บริโภคตรวจสอบร้านได้จากหน้านี้โดยไม่ต้องสมัครสมาชิก | — |
| 2 | ผู้ประกอบการ | `/register` | **กรอกเบอร์โทรศัพท์** — กรอกเบอร์ เช่น 0891234567 ติ๊กยอมรับเงื่อนไข แล้วกด "ขอรหัส OTP" | กรอกเบอร์โทรและกด "ขอรหัส OTP" |
| 3 | ผู้ประกอบการ | `/register` | **ยืนยันรหัส OTP** — กรอก OTP ที่แสดงในกล่องสีเหลือง แล้วกด "ยืนยัน" (ลองกรอกผิดเพื่อแสดงข้อความเตือน)<br>💡 ระบบจริงส่งทาง SMS — ระบบสาธิตแสดงรหัสบนจอ | กรอก OTP ให้ถูกต้องแล้วกด "ยืนยัน" |
| 4 | ผู้ประกอบการ | `/register` | **ข้อมูลเริ่มต้น** — กรอกชื่อ นามสกุล อีเมล และจังหวัด (ข้อมูลสมมติ) แล้วกด "ถัดไป" | กรอกข้อมูลให้ครบแล้วกด "ถัดไป" |
| 5 | ผู้ประกอบการ | `/register` | **ยืนยันบัตรประจำตัว (จำลอง)** — กด "เริ่มยืนยันตัวตน" → "จำลองการถ่ายบัตร" (ติ๊ก "จำลองผลล้มเหลว" ก่อนเริ่ม เพื่อแสดงการ Retry ได้)<br>💡 ไม่เปิดกล้อง ไม่เก็บภาพ และไม่เก็บเลขบัตรประชาชน | ถ่ายบัตรจำลองให้ผ่านขั้นตอน (หากล้มเหลว กด Retry) |
| 6 | ผู้ประกอบการ | `/register` | **สแกนใบหน้า (จำลอง)** — กด "จำลองการสแกนใบหน้า" จนได้ Identity Verified แล้วกด "ดำเนินการต่อ" | ต้องยืนยันตัวตนสำเร็จ (Identity Verified) — กด Retry ได้หากล้มเหลว |
| 7 | ผู้ประกอบการ | `/register` | **ตั้ง PIN 6 หลัก** — ตั้ง PIN และยืนยันให้ตรงกัน (ลอง 111111 ระบบจะปฏิเสธ) | ตั้ง PIN และยืนยันให้ตรงกัน |
| 8 | ผู้ประกอบการ | `/register` | **ลงทะเบียนสำเร็จ** — กด "เข้าสู่หน้าหลัก" บนหน้าจอ | กด "เข้าสู่หน้าหลัก" เพื่อเข้าสู่ระบบด้วยบัญชีที่เพิ่งสร้าง |
| 9 | ผู้ประกอบการ | `/m` | **หน้าหลักผู้ประกอบการ** — ชี้สถานะ "ยืนยันตัวตนแล้ว (Level 1)" และข้อความว่ายังไม่มีร้านค้า<br>💡 Level 1 คือยืนยันตัวตนเจ้าของบัญชีเท่านั้น ไม่ใช่การรับรองคุณภาพสินค้า | — |

**ประโยชน์** — SME: เริ่มต้นได้ภายในไม่กี่นาทีผ่านมือถือ ไม่ต้องเดินทางหรือส่งเอกสารกระดาษ · ผู้บริโภค: มั่นใจได้ว่าร้านค้ามีเจ้าของที่ยืนยันตัวตนแล้ว · สคบ.: ติดตามผู้ประกอบการได้ด้วยตัวตนเดียว แม้เปิดหลายร้านหรือหลายช่องทาง

## สมัครร้านค้าและได้รับการรับรองหลังการตรวจสอบ

**วัตถุประสงค์:** ร้านลงทะเบียนและผ่านการตรวจสอบอัตโนมัติ (ไม่ต้องรอเจ้าหน้าที่) จากนั้นยื่นขอใบรับรอง Business Verified — เจ้าหน้าที่ตรวจตาม Checklist และอนุมัติ ใบรับรองตัวอย่างและ Badge อัปเดตทันที

**กลุ่มผู้ใช้:** ผู้ประกอบการ, เจ้าหน้าที่ · **เวลาโดยประมาณ:** ≈ 7 นาที · **Key Message:** การตรวจสอบเป็นมาตรฐานเดียวกัน มีหลักฐานทุกขั้น และร้านค้านำผลไปใช้บนช่องทางขายเดิมได้

ข้อมูล Marketplace ทั้งหมดเป็นข้อมูลจำลอง ไม่มีการเชื่อมต่อ Shopee/Lazada จริง และผลประเมินเป็นผลจาก Engine ของระบบต้นแบบ (v2.1-sim)

## Demo หลัก — ทดลองใช้งาน SME Trust ตั้งแต่ต้นจนจบ

- เริ่มจากปุ่ม **"ทดลองใช้งาน SME Trust ตั้งแต่ต้นจนจบ"** บนหน้าแรกหรือหน้า Demo — บัญชีตัวอย่าง OP-013 (ยืนยันตัวตนแล้ว ยังไม่มีร้านใน SME Trust แต่มีร้านบน Marketplace จำลอง)
- **เชื่อมข้อมูลร้านค้า:** `/m/register-shop` → **A. เชื่อมต่อร้านค้าจาก Marketplace** → Shopee/Lazada (จำลอง) → หน้าอนุญาตจำลอง (ไม่ใช่หน้า Login ไม่มีช่องรหัสผ่าน) → เลือกร้าน (แนะนำร้าน **"Official"** — ขายมานาน ผลงานดี เพื่อสาธิตกรณีแสดง Badge · ร้าน "Outlet" ที่เพิ่งเปิดได้สถานะข้อมูลยังไม่เพียงพอ) → Preview ข้อมูลต้นฉบับ → ยืนยันนำเข้า
- **ลงทะเบียน:** แบบฟอร์มถูกเติมอัตโนมัติ (ป้ายที่มาของแต่ละช่อง ข้อมูลต้นฉบับอ่านอย่างเดียว) → แก้ "รายละเอียดสินค้าและบริการ" อย่างน้อย 1 จุด **โดยคงชื่อร้านตามร้านบน Marketplace** → ใช้ข้อมูลติดต่อจากบัญชี กรอกอำเภอ แนบเอกสารจำลอง → ติ๊กยืนยัน → "ส่งคำขอ" (ระบบไม่ส่งเอง)
- **ตรวจสอบอัตโนมัติ:** AUTO_PASS → ลงทะเบียนร้านแล้วทันที (`/m/shop`) — **ไม่ออกใบรับรอง Level 2** · ไม่มีงานเจ้าหน้าที่
- **ประเมินความน่าเชื่อถือ + แสดงผล Badge:** `/m/trust` ประเมินด้วย Engine จริงจากข้อมูลที่เชื่อม — Badge แสดงเฉพาะเมื่อผ่านเงื่อนไข (ข้อมูลถึงขั้นต่ำ ยืนยันตัวตนแล้ว ข้อมูลเป็นปัจจุบัน) ไม่เช่นนั้นแสดงสถานะแทน
- **ผู้บริโภคตรวจสอบ:** Role Transition → `/shop/:id` ของร้านเดียวกัน (ผลประเมินที่เปิดเผย สถานะ Badge ช่องทาง Marketplace) → หน้าสรุป → "จบการสาธิต"
- **ชื่อร้านไม่ตรงกับ Marketplace:** ถ้าแก้ชื่อร้านระหว่างทบทวน ปุ่มถัดไปถูกล็อกพร้อมเหตุผล (จะเข้า MANUAL_REVIEW) — คืนชื่อร้านแล้วไปต่อได้ หรือเปิดกรณีพิเศษ · ถ้าส่งคำขอด้วยชื่อที่ไม่ตรงไปแล้ว ขั้น "ตรวจสอบอัตโนมัติ" แสดงผลจริง (MANUAL_REVIEW) พร้อม "เริ่มใหม่ (กลับไปแก้ไข)" / "เปิดกรณีพิเศษ" — ไม่บังคับให้ผ่าน
- **ไม่สร้างร้านซ้ำ:** ย้อนกลับ / Refresh / เปิดหน้าลงทะเบียนอีกครั้งหลังส่งคำขอ → แสดง "ส่งคำขอลงทะเบียนแล้วในการสาธิตนี้" แทนแบบฟอร์ม · เล่นซ้ำล้างร้าน คำขอ การเชื่อมต่อ และบันทึกการนำเข้าของ OP-013 เท่านั้น
- ร้านที่ลงทะเบียนแล้วจัดการช่องทางขาย (เพิ่ม เชื่อม ซิงก์ ยกเลิก Marketplace) ได้ที่เมนู **"ช่องทางขายออนไลน์"** (`/m/marketplace`) — ไม่สร้างร้านใหม่ · หน้าแรกและหน้าหลักผู้ประกอบการพาบัญชีที่มีร้านแล้วไปที่หน้านี้แทนการลงทะเบียนใหม่

## กรณีร้านค้าไม่มี Marketplace และข้อมูลยังไม่พอ

- เริ่มจากการ์ดกรณีพิเศษบนหน้า Demo หรือหน้าแรก → "ทดลองกรณีนี้"
- บัญชีตัวอย่าง OP-012 (ยืนยันตัวตนแล้ว ยังไม่มีร้าน) → ตัวเลือก **B. ลงทะเบียนด้วยตนเอง** → ส่งคำขอ → ระบบผ่านการลงทะเบียนอัตโนมัติ (AUTO_PASS) → ผลประเมิน Insufficient Data (ไม่ใช่ผลลบ) → ผู้บริโภคเห็นสถานะแทน Badge · ไม่มีขั้นตอนเจ้าหน้าที่
- **เล่นซ้ำได้:** ถ้า OP-012 มีร้านจากรอบก่อน หน้ายืนยันการเริ่มแจ้งชื่อร้านที่จะถูกล้างก่อน — ล้างเฉพาะร้านของ OP-012

## คำขอเปลี่ยนชื่อร้าน/หมวด — เดโมเสริม (เผยแพร่แล้ว — Release 3)

เล่นแยก (ไม่อยู่ในตัวควบคุมการสาธิต):

1. บัญชี OP-005 (ร้านกาแฟดอยสูง M-005, Level 3) → เมนู "ช่องทางขายออนไลน์ (Marketplace จำลอง)" → Shopee (จำลอง) → ดูภาพรวมข้อมูล → เปิด `/m/marketplace/profile/<รหัสการเชื่อมต่อ>` (หรือปุ่ม "เติมข้อมูลโปรไฟล์ร้านอัตโนมัติ" หลังเชื่อมต่อ)
2. แก้ "ชื่อร้านที่ใช้แสดง" → ป้าย "รอการตรวจสอบ" → ยืนยันการอัปเดต → ได้ **คำขอเปลี่ยนข้อมูลร้าน PCR-xxx** (ชื่อร้านในโปรไฟล์และใบรับรองยังเป็นชื่อเดิม)
3. สลับเป็นเจ้าหน้าที่ → เมนู "คำขอเปลี่ยนข้อมูลร้าน" → เปิดคำขอ: ตาราง **ข้อมูลเดิม / ข้อมูลใหม่ / ต้นฉบับ Marketplace**, ใบรับรองปัจจุบัน, ประวัติ, Audit Log
4. เลือก **ขอข้อมูลเพิ่มเติม** → สลับเป็นร้านค้า → การแจ้งเตือน → แก้ชื่อร้านและคำอธิบาย (Refresh แล้วฉบับร่างยังอยู่) → "ส่งข้อมูลเพิ่มเติม"
5. เจ้าหน้าที่ **อนุมัติ** → โปรไฟล์ใช้ชื่อใหม่ · ระดับใบรับรองไม่เปลี่ยน · หน้าข้อมูลต้นฉบับยังแสดงชื่อร้านบน Marketplace เดิม · หรือเลือก **ไม่อนุมัติ** (ต้องมีเหตุผล) → ข้อมูลเดิมไม่เปลี่ยน

ประเด็นที่ควรพูด: ไม่อนุมัติอัตโนมัติ · ข้อมูลเดิมใช้ต่อจนกว่าอนุมัติ · Refresh/กดซ้ำไม่สร้างคำขอซ้ำ · รีเซ็ตข้อมูลสาธิตล้างคำขอ

## เครื่องมือสาธิตเพิ่มเติม (P7)

- **ความใหม่ของข้อมูล** — หน้า Data Overview (`/m/marketplace/data/:id`): แสดงอายุข้อมูล ที่มาของวันที่ซิงก์ และ Data Confidence ปัจจุบัน · ปุ่ม "ซิงก์ข้อมูล (จำลอง)" · กล่อง "เครื่องมือสาธิต: จำลองอายุข้อมูล" (ใหม่ / เกิน 30 วัน / เกิน 90 วัน / 180 วัน / ซิงก์ไม่สำเร็จ) — บันทึก Audit ว่าเป็นการจำลอง
- **ชุดน้ำหนัก** — Admin → โมเดลการประเมิน: เลขชุดน้ำหนัก วันที่เริ่มใช้ และประวัติ · ผลประเมินเดิมแสดงชุดน้ำหนักที่ใช้ตอนประเมิน (ไม่ถูกแก้ย้อนหลัง)
- **Dashboard v2** — Admin Dashboard ส่วน "SME Trust v2": KPI การเชื่อมต่อ Band Coverage Confidence และผลการพิจารณา คำนวณจาก State (เปลี่ยนตาม Scenario และกลับค่าเริ่มต้นเมื่อ Reset)

## ข้อควรระวังระหว่างนำเสนอ

- เริ่มการสาธิตจากหน้า Demo เสมอ (ข้อมูลจะกลับเป็นจุดเริ่มต้นของเรื่องนั้น และ ID เริ่มจากค่าตัวอย่าง)
- หน้าแรกของแต่ละเมนูโหลดแยกไฟล์ (Code Splitting) — หน้าอื่นโหลดล่วงหน้าเมื่อเครื่องว่าง จึงควรเปิดแอปทิ้งไว้ครู่หนึ่งก่อนเริ่มนำเสนอหากใช้เครือข่ายช้า
- เว็บไซต์ `/sme-trust/` เป็น v2 — ข้อมูลสาธิตเก็บใต้ localStorage `smetrust:v2:*` ผู้ที่เคยเปิด v1 จะเริ่มด้วยข้อมูลตัวอย่างใหม่ (ข้อมูลของ v1 ไม่ถูกลบ)

## กรณีข้อมูลร้านค้าไม่ตรงกัน — เจ้าหน้าที่ตรวจสอบ (Automation First กรณียกเว้น)

เริ่มจากการ์ดกรณีพิเศษบนหน้าแรกหรือหน้า Demo → "ทดลองกรณีนี้" · ใช้ร้านกาแฟดอยสูง (M-005) ซึ่งเริ่มจากยังไม่ประมวลผล — เส้นทางปกติ (ไม่มีเจ้าหน้าที่) อยู่ใน Demo หลัก

1. เชื่อมแพลตฟอร์มใดก็ได้ → เลือก **"บัญชีร้านเป็นชื่อบุคคลอื่น"** → ยืนยันนำเข้า
2. `/m/trust`: MANUAL_REVIEW — ร้านเห็นเหตุผล (ไม่ใช่การกล่าวหา) · Badge ไม่แสดง
3. เจ้าหน้าที่ `/o/exceptions?tab=identity`: งาน 1 งานพร้อมเหตุผลที่ส่งตรวจ (Refresh ไม่สร้างงานใหม่)
4. เปิดงาน: Evidence Snapshot (เจ้าของบัญชีจาก Raw Source เทียบผู้ยืนยันตัวตน) → อนุมัติ / ไม่อนุมัติ / ขอข้อมูลเพิ่ม
5. กลับมุมร้านค้า: อนุมัติ → Badge แสดง · ไม่อนุมัติ → ข้อมูลร้านนั้นไม่ถูกใช้ (Insufficient Data) · ใบรับรองไม่เปลี่ยนทั้งสองกรณี
6. มุมผู้บริโภค: เห็นสถานะ Badge ล่าสุด ไม่เห็นงานหรือเหตุผลภายใน

**การลงทะเบียนร้านค้าอัตโนมัติ (ใช้ใน Demo หลัก · กรณีร้านไม่มี Marketplace · การสาธิตขอใบรับรอง)** — ระบบตรวจคำขอทันทีหลังร้านกด "ส่งคำขอ":

- **AUTO_PASS** — ข้อมูลครบ ไม่พบความผิดปกติ → ลงทะเบียนร้านแล้ว (ไม่ออกใบรับรอง/Badge การรับรอง)
- **AUTO_REQUEST_INFO** — ข้อมูลยังไม่ครบ (ยังไม่ยืนยันตัวตน / ไม่มีเอกสาร / ไม่มีช่องทางขาย) → ส่งกลับให้ร้านเพิ่มเอง ไม่สร้างงานเจ้าหน้าที่
- **MANUAL_REVIEW** — พบความผิดปกติ (เจ้าของบัญชีร้านไม่ตรงผู้ยืนยันตัวตน · ชื่อร้านต่างจากต้นฉบับ Marketplace) → Officer Exception Queue
- การลงทะเบียน ≠ ใบรับรอง: Level 2 ร้านยื่นแยกและเจ้าหน้าที่อนุมัติ · Assessment และ Assessment Badge ยังเป็นอัตโนมัติ

ประเด็นที่ควรพูด: Demo หลักใช้ 2 บทบาท 0 งานเจ้าหน้าที่ · กรณีข้อมูลไม่ตรงกันใช้ 3 บทบาท 1 งาน · KPI ที่ `/o` และ `/o/automation` คำนวณจากข้อมูลจำลอง ไม่ใช่ผลจากการใช้งานจริง · ระบบประมวลผลเฉพาะเมื่อมีเหตุการณ์ขณะเปิดระบบ (Run Simulation ที่ `/o/automation`)

## เกณฑ์ Band และ Role & Permission (Branch `sme-trustv.2`, ยังไม่เผยแพร่)

- **หน้าแรก → "เกณฑ์การจัดระดับความน่าเชื่อถือ"** (ต่อจาก Trust Assessment ก่อน Assessment Badge): คะแนน 0–100 จาก 5 ปัจจัยพร้อมน้ำหนัก · ตัวอย่าง Risk Signal ที่หักคะแนน · Band A ต้องผ่านครบ 4 ข้อ (คะแนนถึง 80 อย่างเดียวได้สูงสุด B) · B 65–79 · C 50–64 · D < 50 ไม่มี Badge · ข้อมูลขั้นต่ำ 30 คำสั่งซื้อ / 10 รีวิว / 3 เดือน + ยืนยันตัวตนก่อนแสดง Badge → ไม่ครบแสดง "ข้อมูลยังไม่เพียงพอ" (ไม่ได้หมายความว่าร้านค้ามีปัญหา) — ตัวเลขทั้งหมดอ่านจาก Engine `v2.1-sim`
- ประเด็นพูด: ผู้บริโภคเห็นเฉพาะ Band · คะแนนตัวเลขให้เจ้าหน้าที่ใช้ประกอบการพิจารณา · เกณฑ์เป็นค่าเริ่มต้นจากระบบต้นแบบ ปรับร่วมกับหน่วยงานได้
- **Demo Mode → ผู้ดูแลระบบ → เมนู Role & Permission** (`/admin/permissions`): ตารางอ่านอย่างเดียวว่าบทบาทใดทำอะไรได้ พร้อมเส้นทางและฟังก์ชันที่บังคับสิทธิ์ และรายการที่ระบบยังไม่มี
- สาธิตการปฏิเสธ: สลับเป็นผู้บริโภคแล้วเปิด `/o/assessments` → Permission Denied · ความพยายามเรียกฟังก์ชันที่บทบาทนั้นไม่มีสิทธิ์ (ของเจ้าหน้าที่ ผู้บริโภค หรือร้านค้า) ถูกปฏิเสธและบันทึกใน Audit Log ของผู้ดูแลระบบ
- สาธิตการเปิดเผยข้อมูล: หน้าพิจารณาผลประเมินของเจ้าหน้าที่เห็นคะแนน 0–100 และคะแนนที่หัก · ร้านค้า (`/m/trust`) เห็น Band เหตุผล และระดับ Confidence โดยไม่มีตัวเลข · ผู้บริโภค (`/shop/:id`) เห็นเฉพาะ Band/Badge/สถานะ
- หน้าแรก: การยืนยันตัวตนเป็นเงื่อนไขก่อน**แสดง Badge** ไม่ใช่เงื่อนไขคำนวณ Band (ร้านที่ยังไม่ยืนยันแสดง "รอร้านค้าอัปเดตข้อมูล")
- ย้ำผู้ฟัง: การตรวจสิทธิ์ทั้งหมดเป็น **Prototype Simulation บน Browser** — ระบบจริงต้องบังคับสิทธิ์ที่ Backend API
