# Roles & Permissions — บทบาทและสิทธิ์ของ SME Trust

> แหล่งข้อมูลเดียว: [`src/auth/permissions.ts`](../src/auth/permissions.ts) · ดูในระบบได้ที่ **ผู้ดูแลระบบ → Role & Permission** (`/admin/permissions`, อ่านอย่างเดียว)
> ตารางนี้ตรวจอัตโนมัติด้วย `tests/v2/permissions.test.mts` ว่าตรงกับการบังคับสิทธิ์จริง

## บทบาทที่มีในระบบ (จาก `type Role` ใน `src/types/index.ts`)

| บทบาท | รหัส | เข้าสู่ระบบ |
|---|---|---|
| ผู้บริโภค / สาธารณะ | `consumer` | ไม่ต้อง — หน้าตรวจสอบร้านค้าเปิดสาธารณะ · การร้องเรียนใช้บัญชีผู้บริโภคจำลอง |
| ผู้ประกอบการ (เจ้าของร้าน) | `merchant` | ต้องเลือกบัญชีและเข้าสู่ระบบ (PIN / Biometric จำลอง) |
| เจ้าหน้าที่ | `officer` | สลับบทบาทผ่าน Demo Mode |
| ผู้ดูแลระบบ | `admin` | สลับบทบาทผ่าน Demo Mode · มีสิทธิ์ของเจ้าหน้าที่ทั้งหมด |
| ระบบ | `system` | ไม่ใช่บทบาทผู้ใช้ — ใช้บันทึกการกระทำอัตโนมัติ (Automation, ส่งต่อเรื่องอัตโนมัติ) |

**ไม่มีในระบบ:** Supervisor, Approver, Auditor หรือบทบาทอื่น — จึงไม่ได้สร้างเพิ่ม

> ⚠️ **Frontend Authorization ในระบบนี้เป็นเพียง Prototype Simulation** — ระบบไม่มี Backend/API, บทบาทสลับได้จาก Demo Mode และข้อมูลทั้งหมดอยู่ใน `localStorage` ของ Browser
> **ระบบ Production ต้องบังคับสิทธิ์ที่ Backend API ทุกคำขอ** ด้วยตัวตนที่ยืนยันแล้ว (Session/Token ฝั่งเซิร์ฟเวอร์) และต้องตรวจความเป็นเจ้าของข้อมูลด้วย — ตาราง Matrix นี้ใช้เป็นข้อกำหนดตั้งต้นของ API ได้ แต่โค้ดฝั่ง Browser ใช้แทนไม่ได้

## การบังคับสิทธิ์ 2 ชั้น

1. **เส้นทางหน้าจอ** — `RoleGate` ใน `routes/AppRoutes.tsx` (บทบาทไม่ตรง → Permission Denied)
2. **ฟังก์ชันที่เปลี่ยนข้อมูล** — `authorize(permission)` ใน `src/auth/authorize.ts` เรียกเป็นบรรทัดแรกของทุก Action ที่ผู้ใช้เป็นผู้กระทำ: ของเจ้าหน้าที่/ผู้ดูแลระบบ, ของผู้บริโภค และของผู้ประกอบการ (ลงทะเบียน เชื่อมต่อ Marketplace ส่งผลประเมิน ขอเปลี่ยนข้อมูล ขอรับรอง อบรม ฯลฯ) — รวม 52 รายการใน Matrix
   - บทบาทไม่มีสิทธิ์ → `PermissionDeniedError` · **ไม่มีการเปลี่ยนข้อมูล** · บันทึก Audit Log "ปฏิเสธการดำเนินการ (Permission Denied)"
   - การซ่อนเมนูอย่างเดียวจึงไม่ใช่การป้องกัน — ต่อให้เรียกฟังก์ชันตรง ๆ ก็ถูกปฏิเสธ
   - ตรวจจากบทบาทปัจจุบันทุกครั้ง (ไม่ Cache) — สลับบทบาทแล้วสิทธิ์เดิมหมดทันที
   - ข้อความ Error แสดงเฉพาะชื่อสิทธิ์ภาษาไทย ("ไม่มีสิทธิ์ดำเนินการ: …") ไม่มีรหัสสิทธิ์ รหัสรายการ หรือข้อมูลภายใน (รหัสสิทธิ์อยู่ใน `error.permission` สำหรับโค้ด)
   - ฟังก์ชันภายใน Workflow ที่ถูกเรียกต่อจาก Action ที่ตรวจสิทธิ์แล้ว แยกเป็นฟังก์ชันไม่ตรวจซ้ำ เช่น `fileCertificationApplication` (ใช้โดย `submitAssessment` ของร้าน และ `decideAssessment` ของเจ้าหน้าที่) และ `createConnection` / `applyConsent` (ใช้โดย `attachImportedMarketplaces`)
3. **ฟังก์ชันที่ไม่ตรวจบทบาทโดยเจตนา** — ระบุพร้อมเหตุผลใน `UNGUARDED_BY_DESIGN` (`src/auth/permissions.ts`): ฟังก์ชันอ่าน/คำนวณ, ฟังก์ชันภายใน Workflow, ระบบอัตโนมัติ (`processMerchant`, `runAssessment(origin: 'automation')`, `completeSync` ที่จำลองการตอบกลับของแพลตฟอร์ม), การสมัครก่อนเข้าสู่ระบบ (`registerOperator`, `setKycResult`, `resetPin`) และเครื่องมือ Demo — Test บังคับว่าทุกฟังก์ชันที่ export จาก Store ต้องอยู่ใน Matrix หรือรายการนี้

> **ข้อจำกัดสำคัญ:** ระบบเป็น Frontend Prototype ไม่มี Backend/API — ทั้งสองชั้นทำงานในแอปบน Browser และใครก็สลับบทบาทผ่าน Demo Mode ได้ ระบบจริงต้องตรวจสิทธิ์ซ้ำที่ API ฝั่งเซิร์ฟเวอร์ด้วยตัวตนที่ยืนยันแล้ว

## กฎการเปิดเผยข้อมูล (Data Exposure)

| ข้อมูล | ผู้บริโภค | ร้านค้า (ร้านตนเอง) | เจ้าหน้าที่ / Admin |
|---|:-:|:-:|:-:|
| Band, สถานะ Badge, Coverage (%), ระดับ Confidence, สรุปสาธารณะ | ✓ | ✓ | ✓ |
| คะแนนตัวเลข 0–100 / คะแนนรายองค์ประกอบ / ตารางคำนวณ | ✗ | ✗ | ✓ |
| คะแนน Data Confidence (ตัวเลข) | ✗ | ✗ (เห็นระดับ สูง/ปานกลาง/ต่ำ) | ✓ |
| รายละเอียด Risk Signal และหลักฐาน | ✗ | หัวข้อและทิศทางเท่านั้น (ไม่มีคะแนนที่หักและหลักฐาน) | ✓ |
| เหตุผลของ Confidence | ✗ | ✓ ข้อความเหตุผล **ไม่มีคะแนนที่หัก** เช่น "(−15)" | ✓ พร้อมคะแนนที่หัก |
| ข้อมูลการขายและรีวิวดิบ (ร้านของตนเอง) | ✗ | ✓ | ✓ |
| ข้อมูลผู้ร้องเรียน | ผู้ร้องเห็นเรื่องของตนเอง | ชื่อแบบปิดบัง ไม่มีเบอร์โทร/อีเมล | ✓ |
| ผลคัดกรองเรื่องร้องเรียน (Screening) | ตอนส่งเรื่องของตนเอง | ระดับความเร่งด่วนเท่านั้น | ✓ |
| หมายเหตุของเจ้าหน้าที่ | ✗ | เฉพาะข้อความที่ส่งถึงร้าน (เหตุผลไม่อนุมัติ / ขอข้อมูลเพิ่ม) | ✓ |

- หน้าสาธารณะได้ข้อมูลผ่าน `publicAssessmentView()` (`features/trust-assessment/publicView.ts`) เท่านั้น — ไม่มีฟิลด์ `score`, `components`, `riskFactors`, `analysis`, `recommendation` หรือเหตุผลของ Confidence
- มุมมองของร้านค้าใช้ `withoutInternalPoints()` ตัดคะแนนที่หักออกจากข้อความเหตุผล (ทั้ง `/m/trust`, ข้อเสนอของระบบ และการ์ดความใหม่ของข้อมูลใน `/m/marketplace/data/:id`) · หน้าเจ้าหน้าที่ส่ง `internal` จึงเห็นคะแนนที่หักครบ
- **แก้ไข:** (1) เดิมหน้าร้านสาธารณะแสดงเหตุผลของ Data Confidence ซึ่งมีจำนวนคำสั่งซื้อ/รีวิว ตัวเลขหักคะแนน และข้อความสัญญาณ — ตอนนี้แสดงเฉพาะระดับ Confidence · (2) เดิมหน้าร้านค้าแสดงคะแนนที่หัก เช่น "(−30)" และ "Data Confidence ปัจจุบัน: 55" — ตอนนี้แสดงเหตุผลและระดับโดยไม่มีตัวเลขภายใน
- ข้อจำกัด: ข้อมูลทั้งหมดอยู่ใน `localStorage` ของ Browser — Projection ป้องกันการแสดงผลผิดสิทธิ์ แต่ไม่ใช่การป้องกันข้อมูลฝั่งเซิร์ฟเวอร์

## Audit Log

- การกระทำสำคัญบันทึกผ่าน `audit()` อยู่แล้ว (อนุมัติ/ไม่อนุมัติ, ระงับ/เพิกถอน, คำเตือน, ปิดเรื่อง, ตัดสินผลประเมิน, คำขอเปลี่ยนข้อมูล, กรณียกเว้น)
- เพิ่ม: ความพยายามที่ถูกปฏิเสธโดย `authorize()` บันทึกเป็น "ปฏิเสธการดำเนินการ (Permission Denied)" พร้อมบทบาท ชื่อผู้ใช้จำลอง และสิทธิ์ที่ขาด — **ไม่บันทึก** รหัสรายการ ข้อมูลที่ส่งมา คะแนน PIN หรือเลขประจำตัว
- Audit Log เก็บใน Browser — ไม่ใช่ระบบที่ป้องกันการแก้ไขได้จริง

## การทดสอบ

`tests/v2/permissions.test.mts` (รวมใน `npm test`):

- เส้นทางที่ตรวจสิทธิ์ทุกเส้นทางใน `AppRoutes` อยู่ใน Matrix และกลับกัน
- Render ทุกเส้นทาง × 4 บทบาท (276 กรณี) ผลตรงกับ Matrix
- ทุกฟังก์ชันที่ Matrix ระบุว่า 🔒 เรียก `authorize('<สิทธิ์เดียวกัน>')` เป็นบรรทัดแรก
- ผู้บริโภคเข้าหน้าเจ้าหน้าที่/Admin ไม่ได้ · ร้านค้าอนุมัติไม่ได้ (ข้อมูลไม่เปลี่ยน + บันทึก Audit) · การอนุมัติคำขอเปลี่ยนข้อมูลและการดำเนินการข้อร้องเรียนจำกัดตามบทบาท · `setWeights` เฉพาะ Admin
- เจ้าหน้าที่/Admin เห็นคะแนน · ผู้บริโภคและร้านค้าไม่เห็น · Public projection ไม่มีฟิลด์ต้องห้าม
- ทุกฟังก์ชันที่ export จาก Store ถูกจัดประเภท (อยู่ใน Matrix หรือ `UNGUARDED_BY_DESIGN`) — เพิ่มฟังก์ชันใหม่โดยไม่จัดประเภทแล้ว Test ล้มเหลว
- Action ของร้านค้า 18 รายการ × 3 บทบาทอื่น: ถูกปฏิเสธ ข้อมูลทุก Store ไม่เปลี่ยน และมี Audit ของบทบาทนั้น
- ข้อความ Error/Audit ไม่มีข้อมูลภายใน · สลับบทบาทด้วย `switchRole` แล้วสิทธิ์เดิมไม่ค้าง
- Render ทุกหน้าของผู้บริโภคและร้านค้าสำหรับทุกร้าน (480 หน้า): ไม่มีคะแนนตัวเลข คะแนนที่หัก หรือ Confidence ตัวเลข · ร้านค้าไม่เห็นชื่อเต็ม/เบอร์โทร/อีเมลของผู้ร้อง
- หน้าแรก: ตัวเลขทุกตัวตรงกับ Engine · การยืนยันตัวตนแสดงเป็นเงื่อนไขก่อนแสดง Badge (ตาม `ROUTING_POLICY.requireIdentityVerified`) ไม่อยู่ในข้อมูลขั้นต่ำของ Band
- E2E `tests/e2e/band-permissions.spec.ts`: หน้าแรก 375/768/1440 และหน้า Matrix ของ Admin

Test เดิมที่เรียก Workflow โดยตรงถูกปรับให้ทำรายการในนามบทบาทที่ทำได้จริงด้วย `actAs()` (ไม่ได้ลดเงื่อนไขที่ตรวจ) · E2E `v2-p7` เดิมอ่าน "Data Confidence ปัจจุบัน: <ตัวเลข>" ของร้านค้า ซึ่งถูกซ่อนแล้ว จึงตรวจจากเหตุผลที่ Engine ใช้หักความเชื่อมั่น (ข้อมูลเก่า) และตรวจว่ากลับเป็นข้อความเดิมทุกตัวอักษรหลังซิงก์

## ข้อจำกัดที่ยังเหลือ

- **ไม่ตรวจความเป็นเจ้าของ (Ownership) ใน Action ของร้านค้า** — `authorize()` ตรวจบทบาทเท่านั้น หน้าจอแสดงเฉพาะร้านของบัญชีที่เข้าสู่ระบบ แต่การเรียกฟังก์ชันตรงด้วยรหัสร้านอื่นยังทำได้ในบทบาทผู้ประกอบการ (KI-V2-33) — ระบบจริงต้องตรวจที่ API
- **e-KYC จำลองตั้งผลได้จาก Browser** (`setKycResult`) — ระบบจริงต้องรับผลจากผู้ให้บริการ KYC ที่ฝั่งเซิร์ฟเวอร์เท่านั้น (KI-V2-34)
- ทั้งหมดนี้เป็นผลจากการไม่มี Backend — ดูข้อความเตือนด้านบน
