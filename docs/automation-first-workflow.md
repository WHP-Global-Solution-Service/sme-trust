# Automation First, Human by Exception

> ต้นแบบ Frontend-only ด้วยข้อมูลจำลองทั้งหมด — ไม่เชื่อมต่อ Shopee, Lazada หรือ สคบ. จริง ไม่มี Backend และไม่ประมวลผลเมื่อปิดหน้าเว็บ

## 1. หลักการ

งานปกติของ SME Trust ให้ระบบทำเองตั้งแต่ร้านค้านำเข้าข้อมูลจนผู้บริโภคตรวจสอบได้ เจ้าหน้าที่รับเฉพาะกรณีที่:

1. ระบบตัดสินเองอย่างปลอดภัยไม่ได้ (ข้อมูลตัวตนขัดแย้ง หลักฐานขัดแย้ง สัญญาณที่ต้องใช้วิจารณญาณ) หรือ
2. ต้องใช้อำนาจอนุมัติที่ยังไม่ได้มอบให้ระบบ (ใบรับรอง Level 2–4, ชื่อร้าน/หมวดที่ตรวจกับแหล่งอ้างอิงไม่ได้, มาตรการระงับ/เพิกถอน)

ระบบไม่ลดเกณฑ์การประเมิน (ใช้ Trust Assessment Engine v2.1 เดิมทุกข้อ) และไม่ออก ยกระดับ ระงับ หรือเพิกถอนใบรับรองเอง

## 2. กระบวนการอัตโนมัติ (Merchant Self-Service)

| ขั้น | ผู้ทำ | สิ่งที่เกิดขึ้น |
|---|---|---|
| ลงทะเบียน / แก้ไขข้อมูล | ร้านค้า | ตาม Workflow เดิม · ข้อมูลทั่วไปบันทึกทันที |
| เชื่อม Marketplace (จำลอง) | ร้านค้า | ยินยอม → เลือกร้าน → Preview → ยืนยันนำเข้า |
| นำเข้า + Auto-Fill | ระบบ | เติมโปรไฟล์จาก Raw Source (อ่านอย่างเดียว) |
| ตรวจความครบถ้วน + ประเมิน | ระบบ | ประเมินด้วย Engine v2.1 ทันทีเมื่อข้อมูลเปลี่ยน (`origin = automation`) |
| จัดเส้นทาง | ระบบ | Decision Router → AUTO_PASS / AUTO_REQUEST_INFO / MANUAL_REVIEW |
| Assessment Badge | ระบบ | สร้าง/อัปเดตเอง แสดงบนหน้าร้านค้าและต่อผู้บริโภคตามสิทธิ์ |
| ส่งข้อมูลเพิ่ม / ประเมินใหม่ | ร้านค้า | ทำตามรายการที่ระบบแนะนำ · ระบบประเมินซ้ำเองเมื่อข้อมูลเปลี่ยน |

โค้ด: `src/stores/automation.ts` (`processMerchant`, `processAll`, `resolveTask`, `respondToTask`) · Pure: `src/features/automation/{router,derive,policy,kpi}.ts`

## 3. Decision Router

เรียงความสำคัญ: MANUAL_REVIEW > AUTO_REQUEST_INFO > AUTO_PASS (นโยบาย `routing-1.0` ใน `policy.ts`)

| เส้นทาง | เงื่อนไข | การทำงาน |
|---|---|---|
| **AUTO_PASS** | ข้อมูลครบ ยืนยันตัวตนแล้ว ความเชื่อมั่นไม่ต่ำ ข้อมูลไม่หมดอายุ ไม่มีประเด็นที่ต้องส่งตรวจ | อัปเดตผลประเมิน · สร้าง/อัปเดต Badge · แจ้งร้าน · **ไม่สร้างงานเจ้าหน้าที่** |
| **AUTO_REQUEST_INFO** | Insufficient Data · ความเชื่อมั่นต่ำ · ข้อมูลซิงก์เก่ากว่า 90 วัน · ยังไม่ยืนยันตัวตน | แจ้งร้านพร้อมสิ่งที่ต้องเพิ่มและลิงก์ไปทำเอง · ประเมินซ้ำเมื่อข้อมูลเปลี่ยน · ไม่สร้างงานเจ้าหน้าที่ |
| **MANUAL_REVIEW** | ชื่อเจ้าของบัญชีร้านไม่ตรงกับผู้ยืนยันตัวตน · สัญญาณร่วม (`risk.cross`) หรือข้อร้องเรียนเร่งด่วนที่ยังไม่ปิด · สัญญาณทั่วไป ≥ 2 ข้อพร้อมกัน · คะแนนรีวิวต่างกันระหว่างแพลตฟอร์ม ≥ 0.8 ดาว · มีมาตรการ/เรื่องพิจารณาความเสี่ยงอยู่แล้ว | สร้างงาน 1 งานต่อประเด็น + Evidence Snapshot + เหตุผล + ลำดับความสำคัญ · Approve / Reject / Request Info · Audit Log |

ข้อสังเกต (ไม่เปลี่ยนเส้นทาง): สัญญาณทั่วไปข้อเดียว (Engine จำกัด Band สูงสุด B อยู่แล้ว) · ซิงก์บางแพลตฟอร์มไม่สำเร็จ

**การคัดกรองไม่ใช่การตัดสินว่าร้านค้าทุจริต** — ข้อความทุกจุดระบุว่าเป็นข้อสังเกตจากข้อมูล และระบบไม่สามารถตรวจจับการทุจริตได้แน่นอน

### กันงานซ้ำ

- หนึ่งงานเปิดต่อร้านต่อประเภทประเด็น — ประเด็นเดิมที่ข้อมูลเปลี่ยนจะอัปเดตหลักฐานในงานเดิม
- ประเด็นมี **Fingerprint** (เช่น `identity:<connection>:<owner>`, `risk:<signal ids>`) — เจ้าหน้าที่อนุมัติแล้วจะไม่ส่งซ้ำจนกว่าข้อมูลจะเปลี่ยน (Fingerprint ใหม่)
- ประเด็นของร้านที่มีมาตรการ/เรื่องพิจารณาความเสี่ยงอยู่แล้ว **รวมเข้ากับเรื่องเดิม** (ไม่สร้างงานใหม่ และปิดงานที่ค้างพร้อมเหตุผล)
- ประเด็นหายไปเพราะข้อมูลเปลี่ยน → ปิดงานอัตโนมัติพร้อมเหตุผล
- ประมวลผลซ้ำ / Refresh / Run Simulation ด้วยข้อมูลเดิม → ไม่สร้างผลประเมิน งาน ประวัติ Badge หรือการแจ้งเตือนใหม่

## 4. Trust Assessment Badge

| สถานะ | เมื่อไร | ผู้บริโภคเห็น |
|---|---|---|
| `active` | AUTO_PASS และ Band A/B/C | Badge + Band + Coverage + Confidence + วันที่ + Model Version |
| `below_threshold` | Band D | ผลประเมินตามเดิม (ไม่มี Badge) |
| `insufficient` | ข้อมูลไม่พอ | "ข้อมูลยังไม่เพียงพอ — ไม่ได้หมายความว่าร้านมีปัญหา" |
| `needs_update` | AUTO_REQUEST_INFO อื่น ๆ | ร้านกำลังอัปเดตข้อมูล |
| `under_review` | MANUAL_REVIEW (ระบบส่งตรวจ) | อยู่ระหว่างตรวจสอบเพิ่มเติม — **ไม่แสดง Band** (ข้อมูลอาจไม่ใช่ของร้าน) |
| `withheld` | มีเรื่องพิจารณาความเสี่ยงเปิดอยู่ | ระงับการแสดงระหว่างพิจารณา (Band + Standing ตามเดิม) |
| `suspended` / `revoked` | ใบรับรองถูกระงับ/เพิกถอน | ไม่แสดง Badge แม้ผลประเมินสูง |

- หนึ่ง Badge ต่อร้าน (`TAB-<merchantId>`) · ประวัติบันทึกเมื่อสถานะ/Band/ความเชื่อมั่นเปลี่ยนเท่านั้น พร้อมเหตุการณ์ ผลประเมิน และ Model Version
- ผู้บริโภคไม่เห็นคะแนนภายใน เส้นทางของระบบ หรืองานของเจ้าหน้าที่
- **ไม่มีการสร้าง Certification Badge อัตโนมัติ** และข้อความทุกจุดระบุว่า Assessment Badge ไม่ใช่การรับรอง

## 5. Officer Responsibilities

| งาน | ที่มา | หน้าจอ |
|---|---|---|
| Identity Mismatch / Evidence Conflict / Risk Signals | Decision Router (`officer-tasks`) | `/o/exceptions`, `/o/exceptions/:id` |
| คำขอลงทะเบียน (Level 2) / คำขอรับรอง (Level 3–4) / ผลประเมินรอพิจารณา | Workflow เดิม (Certification Policy) | `/o/applications`, `/o/assessments` |
| ชื่อร้าน/หมวดที่ตรวจกับแหล่งอ้างอิงไม่ได้ | Workflow คำขอเปลี่ยนข้อมูลร้าน (KI-V2-15) | `/o/profile-changes` |
| ข้อร้องเรียนส่งต่อ / ข้อกล่าวหา / อุทธรณ์ | Workflow เดิม | `/o/complaints`, `/o/risk` |

Exception Queue รวมทุกอย่างข้างต้นเป็นหมวด: Pending Manual Review · High Priority · Identity Mismatch · Evidence Conflicts · Risk Signals · Certification Requests · Escalated Complaints · Completed Reviews (งานเดิมลิงก์ไปที่เรื่องเดิม ไม่คัดลอกเป็นงานใหม่)

ผลการตัดสินงานจาก Decision Router:

| ประเภท | อนุมัติ | ไม่อนุมัติ | ขอข้อมูลเพิ่ม |
|---|---|---|---|
| Identity Mismatch | ยืนยันเป็นร้านเดียวกัน → ใช้ข้อมูลประเมิน → Badge | ข้อมูลจากการเชื่อมต่อนี้ไม่ถูกใช้ประเมิน (ใบรับรองไม่เปลี่ยน) | ร้านตอบในงานเดิม → งานกลับเข้าคิว |
| Evidence Conflict / Risk Signal | ตรวจแล้วไม่ต้องดำเนินการ (Fingerprint ถูกบันทึก) | เปิดเรื่องพิจารณาความเสี่ยงตามกระบวนการเดิม (ร้านชี้แจง/อุทธรณ์ได้ — **ไม่ระงับอัตโนมัติ**) | เหมือนข้างต้น |

ทุกการตัดสินต้องมีเหตุผล ≥ 5 ตัวอักษร · บันทึก Audit Log · แจ้งร้านค้า · ระบบประมวลผลร้านใหม่ทันที

## 6. Merchant Profile Change Automation

| ข้อมูล | กฎ |
|---|---|
| ทั่วไป (คำอธิบาย ติดต่อ ที่อยู่) | บันทึกอัตโนมัติ |
| ชื่อร้าน/หมวดที่ผูกกับใบรับรอง และ**ตรงกับข้อมูลต้นฉบับ Marketplace** ที่ร้านยินยอมให้เชื่อม | สถานะ `source_verified` → บันทึกโดยไม่ต้องรอเจ้าหน้าที่ + Audit Log "ตรวจสอบข้อมูลร้านอัตโนมัติ" |
| ชื่อร้าน/หมวดที่ตรวจกับแหล่งอ้างอิงไม่ได้ | คำขอเปลี่ยนข้อมูลร้าน (Exception) — ข้อมูลเดิมใช้ต่อจนกว่าอนุมัติ |
| ข้อมูลต้นฉบับ Marketplace | อ่านอย่างเดียว — ร้านแก้ไม่ได้ และการแก้โปรไฟล์ไม่เปลี่ยน Snapshot/ผลวิเคราะห์ที่ใช้ประเมิน |

## 7. Certification Governance

| Level | การดำเนินการ (ค่าเริ่มต้นของ Prototype = กฎเดิม) |
|---|---|
| 1 Identity Verified | อัตโนมัติจากผล e-KYC (จำลอง) — กฎเดิมของระบบ |
| 2 Business Verified | เจ้าหน้าที่อนุมัติคำขอลงทะเบียน |
| 3 Trusted SME | เจ้าหน้าที่อนุมัติ + เกณฑ์ v1 · ผลประเมินใช้ประกอบเท่านั้น |
| 4 Trusted SME Plus | เจ้าหน้าที่อนุมัติ |

`CERTIFICATION_POLICY` มีช่อง `autoApprovalAuthorized` (ค่าเริ่มต้น `false` สำหรับ Level 2–4) — การเปิดอนุมัติอัตโนมัติต้องมีนโยบายและอำนาจที่ได้รับอนุมัติก่อน ต้นแบบนี้**ไม่เปลี่ยนกฎการอนุมัติเดิม**

แยกเสมอ: **Assessment Badge** (ผลประเมินอัตโนมัติ) · **Certification Badge** (สถานะการรับรอง) · **Suspension / Revocation** (มาตรการของเจ้าหน้าที่)

## 8. Automatic Monitoring (Event-based)

ระบบประมวลผลเมื่อมีเหตุการณ์ขณะผู้ใช้เปิดระบบ:

| เหตุการณ์ | ประเมินใหม่ | หมายเหตุ |
|---|---|---|
| นำเข้า / ซิงก์สำเร็จ / ซิงก์ไม่สำเร็จ / จำลองอายุข้อมูล / ยกเลิกการเชื่อมต่อ | ✅ เมื่อข้อมูลเปลี่ยน | ตรวจอายุข้อมูลและสัญญาณ · แจ้งเตือนเฉพาะเมื่อผลเปลี่ยน |
| อัปเดตโปรไฟล์ / อนุมัติเปลี่ยนข้อมูลร้าน | ✅ เมื่อข้อมูลเปลี่ยน | |
| ร้านกดประเมินเอง | ใช้ผลที่ร้านประเมิน | จัดเส้นทางและอัปเดต Badge ต่อ |
| เจ้าหน้าที่ตัดสินกรณียกเว้น / ผลประเมิน | ✅ / ใช้ผลล่าสุด | |
| ระงับ / เพิกถอน / คืนสถานะ / เรื่องพิจารณาความเสี่ยง (Workflow เดิม) | ใช้ผลล่าสุด | Badge อัปเดตทันทีผ่าน `stores/events.ts` |
| ยืนยันตัวตน | ✅ | |
| **Run Simulation** (`/o/automation`) | ✅ ทุกร้าน | จำลองการประมวลผลตามรอบ |

**ข้อจำกัด:** Frontend Prototype ไม่ประมวลผลตลอด 24 ชั่วโมงเมื่อปิดหน้าเว็บ และไม่ได้ติดตามร้านค้าจริงแบบ Real-time

## 9. KPI (จาก Mock State)

`/o` และ `/o/automation`: ร้านที่ผ่านอัตโนมัติ · ร้านที่ต้องเพิ่มข้อมูลเอง · ร้านที่ส่งเจ้าหน้าที่ · อัตราส่วน Manual Review · งานที่สร้าง/ปิดแล้ว — คำนวณจากผลการประมวลผลล่าสุดของแต่ละร้าน **ไม่ใช่ผลการลดภาระงานที่วัดจากการใช้งานจริง**

ข้อมูลตั้งต้น: ประมวลผล 10 ร้าน → ผ่าน 5 · เพิ่มข้อมูลเอง 1 · ส่งเจ้าหน้าที่ 4 (ทั้ง 4 ร้านมีมาตรการ/เรื่องพิจารณาความเสี่ยงอยู่แล้ว จึงไม่มีงานใหม่)

## 11. ข้อจำกัดของต้นแบบ

- ข้อมูลทั้งหมดเป็นข้อมูลจำลอง ชื่อเจ้าของบัญชีร้านเป็นชื่อสมมติที่ระบุ "(จำลอง)"
- กฎ Decision Router เป็นค่าตั้งต้นเพื่อการสาธิต ยังไม่ผ่านการทดสอบกับข้อมูลจริง และไม่ใช่ระบบตรวจจับการทุจริต
- นโยบายเป็นค่าคงที่ในโค้ด (อ่านอย่างเดียวในหน้าจอ) — ยังไม่มีหน้าปรับนโยบายพร้อมการอนุมัติ
- เจ้าหน้าที่ทุกคนเห็นคิวเดียวกัน (ยังไม่มีการมอบหมายงานรายบุคคลหรือ SLA)
